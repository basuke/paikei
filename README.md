# Paikei（牌景）

麻雀の局面を解析する Swift ライブラリ **PaikeiCore** と CLI **paikei**。

局面を1枚のスナップショットとして受け取り、シャンテン数・受け入れ・何切る・役と点数・
フリテン・安牌・鳴ける手を返す。Swift 6 / SwiftPM、macOS と Linux で動く。

最終的な目標は iOS アプリ **Paikei** — カメラで雀卓を撮ると牌を認識し、その瞬間の局面に
ついてあらゆる解析を返す。このリポジトリはその**ロジック層**にあたる。認識層（Vision /
Core ML）とはテキストフォーマット **`.paikei`** で疎結合にしてあり、認識層の完成を待たずに
ロジック層だけを完成・検証できる。

```
[カメラ認識層]──┐
[MJAI牌譜]────┼──> .paikei ──> [PaikeiCore] ──> 解析結果
[手入力/REPL]──┘                (このリポジトリ)
```

## できること

| | |
|---|---|
| シャンテン・受け入れ | 一般形 / 七対子 / 国士。既知の正解データ4万手と照合済み |
| 何切る | 全打牌候補を「シャンテン → 受け入れ枚数」で比較 |
| 和了・役・符・点数 | 面子分解の全列挙 → 役判定 → 高点法。役満の複合と包（責任払い）まで |
| フリテン | 論理捨て牌履歴（河 + 鳴かれた牌）から判定。同巡内フリテンは履歴込み |
| 安牌 | 現物 / スジ / 壁。立直後に通った牌も履歴から拾う |
| 鳴ける手 | ロン・ポン・チー・大明槓の候補列挙。槍槓の文脈も区別する |
| 局の再生 | 初期局面 + イベント列。任意の時点まで巻き戻して解析できる |
| 対局の進行 | 半荘・東風戦。連荘/親流れ・本場・供託・点数移動・終局判定 |
| MJAI bot | 標準入出力で JSON Lines を読み書きし、シミュレータと対局する |

### 「不明」を第一級に扱う

カメラ由来の局面は必ず一部が読めない。だから解析関数は不足情報があるとき、
**仮定を明示して答える**か、**必要な情報を宣言して断る**。黙って推測しない。

たとえば場風が不明なとき、東南西北を総当たりして役と符が全候補で一致すれば
仮定は答えを変えないので黙って進む。1つでも違えば「場風が要る」と言って断る。
「東場と仮定」で済ませると、実際が南場なら役を捏造してしまうため。

#### 牌の表示

既定は漢字（`1萬` `5筒` `東`）。`PAIKEI_TILES=unicode` で Unicode の麻雀牌
（U+1F000〜）に切り替わる。REPL なら `tiles unicode`。

```console
$ PAIKEI_TILES=unicode paikei shanten east2-1.paikei
何切る:
  打 🀔 → 1シャンテン 受け入れ 🀐 🀓 🀕 🀗 🀘 = 15枚
  打 🀗 → 1シャンテン 受け入れ 🀐 🀓 🀕 🀘 = 13枚
```

フォントが対応していないと豆腐になるので既定にはしていない。
赤5は対応する符号位置が無いため `🀝~` と表す（端末なら赤字）。

### REPL

引数なしで起動すると対話モードに入る。局面を読み込み、解析し、打牌や鳴きで進め、
そのまま保存できる（初期局面 + 操作履歴が `.paikei` になる）。

```console
$ paikei
> load east2-1.paikei
> shanten
> safety shimocha
> discard 1z            # 状態遷移（イベントを生成）
> options               # いま鳴ける手
> seek 3                # 3イベント目まで巻き戻して解析
> save session.paikei
```

### MJAI bot

```console
$ cat game.jsonl | paikei mjai
{"type":"join","name":"Paikei","room":"default"}
{"type":"none"}
{"type":"dahai","actor":2,"pai":"9s","tsumogiri":true}
{"type":"hora","actor":2,"target":3,"pai":"5s"}
```

同梱の打ち手（`SimpleBot`）は受け入れ最大の牌を切り、和了れるときだけ和了る最小の実装。
鳴かず立直せず、安全度も見ない。プロトコル接続と進行の検証が目的の基準線。

## テキストフォーマット `.paikei`

局面を人間が読み書きできる1つのテキストにする。正典は
[`docs/PAIKEI_SPEC.md`](docs/PAIKEI_SPEC.md)。

```
# east2-1.paikei — 東2局1本場、下家リーチ、対面ポンあり
bakaze: E
kyoku: 2
honba: 1
kyotaku: 1
dora_markers: 3p
wall: 42

[self] seat=W
hand: 234m567p23788s11z
draw: 0s
river: 1z 9m 1p 9p
score: 24000

[shimocha] seat=N
river: 9s 1z 2z 4m* 6p     # 4m* はリーチ宣言牌
riichi: true
score: 26300

[toimen] seat=E
melds: pon(5'55p,L)        # 上家から赤5筒をポン
river: 1z 3z 9m 1s 2s
score: 25700
```

チェスの PGN のように、初期局面に続けてイベント列を書ける（`[stream]` セクション）。
MJAI 生ログをそのまま貼れる方言も用意してある。

## ライブラリの構成

```
Sources/PaikeiCore/
  Rules/     卓の取り決め1枚（1局のルールと対局のルール）
  Model/     牌・風・プレイヤー・副露・河（局にも対局にも属さない素材）
  Game/      局面・イベント・時系列・局の結末
  Shanten/   シャンテン数・受け入れ・何切る
  Agari/     面子分解・役・平和・和了形の読み
  Scoring/   符・点数・ドラ・応答の選択肢
  Safety/    論理捨て牌履歴・フリテン・安牌・見えている牌
  Format/    .paikei の入出力（Notation/ は牌・副露・河の表記、Stream/ はイベント列と MJAI 方言）
  Bot/       局面から手を決める打ち手
  Match/     局の連鎖（半荘・東風戦）
Sources/paikei/   CLI（1発実行・REPL・MJAI bot）
```

依存は常に **Format → ドメイン層** の一方向。フォーマットは入出力の1形式にすぎないので、
Model 以下はフォーマットの型を一切知らない。全て値型で、ロジックは純粋関数。

### コードは日本語で書いてある

Swift の Unicode 識別子を積極的に使い、麻雀の概念はそのまま日本語で書く。
変数名は英数字のままにして、case・関数名・テスト名を日本語にする。
ラベルは牌や属性が日本語、プレイヤーの役割は英語の前置詞（`of:` / `from:`）。

```swift
case ポン(of: Player, from: Player, 牌: Tile, 手牌から: [Tile])

if try timeline.可能な応答(for: player).contains(.ロン) {
    return .和了(of: player, from: discarder, 牌: tile)
}
```

## 現在地

コアの解析は一通り動き（[実装フェーズ](CLAUDE.md#実装フェーズと現在地) 1〜7 完了）、
半荘・東風戦の進行まで乗った。テスト387件。

残しているのは**裁定**（応答の優先順位・頭ハネ、途中流局の成立、テンパイ判定）で、
これは卓を回す側の担当として切り出してある。これからは実データでの検証と、
打ち手の質を上げるところ。
