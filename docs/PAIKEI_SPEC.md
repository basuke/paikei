# Paikei（牌景）フォーマット仕様 v0.1 (draft)

リーチ麻雀の**ある瞬間の卓上の状態（スナップショット）**を記述するテキストフォーマット。

チェスのFEN、将棋のSFENに相当するものとして設計するが、麻雀は不完全情報ゲームであり、
観測手段（カメラ / 牌譜 / 手入力）によって得られる情報が異なるため、
**「観測できたものだけを正直に書き、不明を明示できる」**ことを第一原則とする。

- ファイル拡張子: `.paikei`
- 文字エンコーディング: UTF-8
- 1ファイル = 1スナップショット + 任意のイベントストリーム（§8）

---

## 1. 設計原則

1. **カメラの真実**: 物理的に卓上に見えるものをそのまま書く。見えないものは書かない。
2. **不明の明示**: 値が観測できなかった場合は `?`（フィールド値）または無印（牌の属性）で「不明」を表す。
   「省略 = デフォルト値」ではなく「省略 = 不明」。
3. **導出は読み手の仕事**: 論理的捨て牌履歴・フリテン・ドラ・残り枚数などは、
   記述された物理情報から**導出する**。フォーマットには書かない。
4. **相互運用性**: 牌の表記はMPSZ、フィールド名はMJAIプロトコルに寄せる。

### 情報の3階層

| 階層 | 内容 | カメラ | MJAI牌譜 |
|------|------|:------:|:--------:|
| 物理層 | 牌の種類・位置・向き | ○ | ○ |
| 導出層 | 論理捨て牌履歴、フリテン、ドラ、残り枚数 | 導出 | 導出 |
| 履歴層 | 手出し/ツモ切り、鳴かれた位置、一発の有無 | ×（動画なら一部○） | ○ |

履歴層の情報はオプショナル。書かれていれば利用し、無ければ「不明」として扱う。

## 2. 牌の表記（MPSZ形式）

| 表記 | 意味 |
|------|------|
| `1m`〜`9m` | 萬子 1〜9 |
| `1p`〜`9p` | 筒子 1〜9 |
| `1s`〜`9s` | 索子 1〜9 |
| `1z`〜`7z` | 字牌（東南西北白發中の順） |
| `0m` `0p` `0s` | 赤5 |

### 連結表記と分離表記

- **手牌**（`hand:`）は連結表記。同スートの連続はスート文字を末尾に1回だけ書ける:
  `123m456p789s11z`
- **河**（`river:`）は分離表記。1枚ずつスペース区切り: `1z 9m 1p 9p`
  （河は順序と牌ごとの属性が意味を持つため省略記法を使わない）
- パーサーはどちらの文脈でも赤5の `0` を受理する。正規化出力時、`0` は同種の `5` の直前に置く
  （例: `44056m` → `4m 4m 0m 5m 6m`）。

## 3. ファイル構造

行ベースのフォーマット。

- `key: value` — フィールド行
- `[player]` — プレイヤーセクション開始
- `# ...` — コメント（行頭または行末。`#` 以降を無視）
- 空行は無視
- キーはすべて小文字。値の前後の空白は無視

### 3.1 卓全体フィールド（プレイヤーセクションより前に書く）

| キー | 値 | 例 | 説明 |
|------|-----|-----|------|
| `bakaze` | `E` `S` `W` `N` / `?` | `E` | 場風 |
| `kyoku` | 1〜4 / `?` | `2` | 局数 |
| `honba` | 0以上の整数 / `?` | `1` | 本場 |
| `kyotaku` | 0以上の整数 / `?` | `1` | 供託リーチ棒 |
| `dora_markers` | 牌のスペース区切り / `?` | `3p 7s` | ドラ**表示**牌。カン分は複数 |
| `wall` | 0以上の整数 / `?` | `42` | 山の残り枚数（王牌除く） |
| `rule` | 識別子 / `?` | `default` | ルールプリセット名（将来拡張用） |

すべてオプショナル。書かれていないフィールドは `?` と同義。

### 3.2 プレイヤーセクション

`[self]` `[shimocha]` `[toimen]` `[kamicha]` の4種。**カメラ相対の位置**を主キーとする。
出現順は任意だが、正規化出力は self → shimocha → toimen → kamicha の順。
`[self]` 以外は省略可（省略 = そのプレイヤーの情報はすべて不明）。

セクションヘッダには属性を付けられる:

```
[shimocha] seat=N
```

| 属性 | 値 | 説明 |
|------|-----|------|
| `seat` | `E` `S` `W` `N` / `?` | 席風。親は `seat=E` から導出（`oya` フィールドは持たない） |

### 3.3 プレイヤーフィールド

| キー | 値 | 例 | 説明 |
|------|-----|-----|------|
| `hand` | 連結MPSZ / `?` | `234m567p23788s11z` | 手牌（純手牌のみ、副露を含まない）。通常 `[self]` のみ |
| `draw` | 牌1枚 | `0s` | ツモ牌（14枚目）。ツモ直後でなければ省略 |
| `melds` | 副露のスペース区切り | `pon(5'55p,L)` | §4参照。左から古い順 |
| `river` | 牌+属性のスペース区切り | `1z- 9m+ 4m+* 6p` | 捨て牌。左から古い順。§5参照 |
| `riichi` | `true` / `false` / `?` | `true` | リーチ宣言済みか。省略時 `?`（riverの `*` から導出可能な場合は導出） |
| `score` | 整数 / `?` | `24000` | 持ち点 |
| `discard_context` | `draw` / `call` / `?` | `call` | 14枚目の由来（§7参照）。`draw:` があれば `draw` と同義。省略時 `?` |

### 3.4 局面イベントフィールド（卓全体、オプショナル）

他家のアクションに対する判断（ロン・鳴き）を問う局面のためのフィールド:

```
claim_tile: 6p from=shimocha kind=discard
```

「いま `shimocha` が `6p` を出した直後」を表す。この牌はまだ誰の河にも確定していない
（記述上は打牌者の `river:` 末尾に**含めない**）。`draw:` とは排他。

| 属性 | 値 | 説明 |
|------|-----|------|
| `from` | プレイヤー名 | 必須。牌を出したプレイヤー |
| `kind` | `discard` / `riichi` / `kakan` / `ankan` | 省略時 `discard` |

イベントストリーム（§8）を適用するときも、**打牌イベントは必ずこの状態を経由する**。
打った牌は即座に河へ入らず応答対象となり、次のイベントで決着する:

- 誰も反応しなければ打牌者の河へ確定する（属性はそのまま引き継ぐ）
- 鳴かれた場合は河に `^` 付きで残る（実物は副露側。物理カウントからは除外、§5）

`claim_tile:` は手出し/ツモ切りを表記できないため、ファイル経由では打牌属性が
失われる（履歴層はオプショナル、§1）。

- `discard`: 通常の打牌。ロン/ポン/カン/チーが検討対象
- `riichi`: リーチ宣言牌。スルーされるとリーチ成立（供託+1、一発区間開始）という遷移が特殊
- `kakan`: 加槓された牌。**槍槓ロンのみ**が検討対象
- `ankan`: 暗槓された牌。**国士無双の槍槓のみ**が検討対象（ルール依存）

## 4. 副露（melds）の表記

形式: `種類(牌列,方向)`

| 種類 | 例 | 方向 | 説明 |
|------|-----|------|------|
| `chi` | `chi(6'78p)` | 不要（常に上家） | チー |
| `pon` | `pon(5'55p,L)` | 必須 | ポン |
| `daiminkan` | `daiminkan(9'999s,C)` | 必須 | 大明槓 |
| `kakan` | `kakan(5'555p,L)` | 必須（元のポンの方向） | 加槓 |
| `ankan` | `ankan(9999s)` | なし | 暗槓 |

- 方向: `L` = 上家(kamicha) / `C` = 対面(toimen) / `R` = 下家(shimocha) から鳴いた
- `'`（アポストロフィ後置）= **鳴いた牌**（実卓で横向きの牌）。直前の1枚に付く
- `'` は赤5の帰属を確定するために重要: `pon(0'55p,L)`（上家が赤を捨てた）と
  `pon(05'5p,L)`（赤は自分の手にあった）は区別される
- 牌列内の表記は連結MPSZ（スート文字は末尾に1回）
- `kakan` の `'` は元のポンで鳴いた牌に付ける。加槓で足した牌は牌列の最後に置く

## 5. 河（river）の牌属性

牌の直後に属性文字を後置する。複数付ける場合の順序は **打牌属性 → 状態属性**。

### 打牌属性（履歴層 — ソースが知っている場合のみ）

| 記号 | 意味 |
|------|------|
| `+` | 手出し |
| `-` | ツモ切り |
| 無印 | 不明 |

### 状態属性（物理層/履歴層）

| 記号 | 意味 | 出所 |
|------|------|------|
| `*` | リーチ宣言牌（実卓で横向きの牌） | カメラ / 牌譜 |
| `^` | この位置で捨てられたが**鳴かれて物理的に不在** | 牌譜のみ |

例:

```
river: 1z- 9m+ 5p-^ 4m+* 6p
#      │   │   │     │    └ 属性不明（カメラ由来）
#      │   │   │     └ 手出しでリーチ宣言
#      │   │   └ ツモ切りしたが鳴かれた（実物は鳴いた人の副露にある）
#      │   └ 手出し
#      └ ツモ切り
```

### セマンティクス

- **論理的捨て牌履歴**（フリテン・現物判定に使う）:
  `river の全牌（^含む）∪ 副露から導出される「このプレイヤーから鳴かれた牌」`
  - 副露の被鳴き牌の帰属: `pon(...,L)` の `'` 牌は「副露者の上家」の捨て牌、
    `chi` は常に上家の捨て牌、のように機械的に導出する
- **物理的枚数カウント**（山読み・壁の判定に使う）:
  `^` 付きの牌は除外する（実物は副露側で数える）
- カメラ由来のスナップショットに `^` は現れない。鳴かれた牌の存在は副露から導出される
  （河のどの位置だったかは不明のまま — これも「観測の限界を正直に書く」の一部）
- リーチ宣言牌が鳴かれた場合、実卓では次の捨て牌を横に曲げる。カメラは見えたとおり
  横向きの牌に `*` を付ける。牌譜由来では真の宣言牌に `^*` を付けられる

## 6. 不明値 `?` の扱い

- フィールド値の `?` は「観測できなかった」を意味する
- 解析コマンドは、不明値があっても**答えられる範囲で答える**。ただし
  **仮定で答えが誤るくらいなら断る**:
  - 手牌だけあればシャンテン計算は可能
  - 不明値を仮定で埋めてよいのは、**外れていても答えがより低く出るだけ**の場合に限る
    （本場・供託・ドラ・立直の不明）。置いた仮定は必ず注記する
  - 仮定次第で答えが誤りうる場合は、仮定せず不足している情報を宣言して断る。
    典型は場風・自風で、役牌が付くかどうかが変わる。不明な風は東南西北を
    総当たりし、**役と符が全候補で一致するなら**答えは変わらないので仮定してよい
    （国士無双や、風牌を含まない手）
  - 席風の親子の別（＝支払い）だけは「子」と仮定してよい。上の総当たりを
    通った場合に限られるため、誤りうるのは支払いのみで、役・符は正しい
  - 解析が置いた和了の前提（和了牌・自摸/ロン）を局面が裏づけていないときも注記する。
    静止状態での「この牌が出たら？」の試算や、`draw:` / `claim_tile:` と食い違う指定がこれにあたる
- 実装は「各解析が必要とする情報」を宣言し、不足時は仮定を明示するか不足を報告する

## 7. 局面フェーズ（Phase）と導出

スナップショットが切り取る瞬間は、麻雀のターン構造上の3つのフェーズのいずれかに分類できる。
フェーズはフィールドの有無から**導出**され、有効な解析コマンドと状態遷移を規定する。

### 7.1 フェーズの導出規則

| 条件（優先順） | フェーズ |
|----------------|----------|
| `claim_tile:` がある | **応答待ち**（awaiting claim） |
| `draw:` がある、または手牌に14枚目相当がある | **打牌待ち**（awaiting discard） |
| どちらもない | **静止状態**（quiescent） |

「14枚目相当」の判定: あるプレイヤーの純手牌の枚数が `13 − 3 × 副露数 + 1` であること。

### 7.2 静止状態（quiescent）

直前の打牌に誰も反応せず、次のツモが行われる前。全員が `13 − 3 × 副露数` 枚。
カメラで撮影したスナップショットのデフォルトは通常この状態。
有効な解析: `shanten` / `waits` / `furiten` / `safety` / `analyze`（13枚形）など静的解析全般。

### 7.3 打牌待ち（awaiting discard）

いずれかのプレイヤーが14枚目を持ち、打牌を選択中。文脈により可能なアクションが変わる:

| context | 状況 | 可能なアクション |
|---------|------|------------------|
| `draw` | ツモ直後 | 打牌 / ツモ和了 / リーチ宣言 / 暗槓・加槓 /（第一ツモなら九種九牌） |
| `draw`（リーチ後） | `riichi: true` でのツモ | ツモ和了 / 暗槓（待ちが変わらない場合のみ）/ ツモ切り |
| `call` | 鳴いた直後 | 打牌のみ（ツモ和了不可、喰い替え制限あり） |
| `?` | 不明 | 解析側は仮定を注記して答える |

導出規則:

- `draw:` があれば context = `draw`（`riichi: true` ならリーチ後ツモ）
- `draw:` がなく手牌に14枚目相当がある場合、「鳴いた直後」と「ツモ牌を手牌に混ぜた後」は
  **カメラから区別できない** → context = `?`。ソースが知っている場合（MJAI由来など）は
  `discard_context:` フィールドで明示する

### 7.4 応答待ち（awaiting claim）

`claim_tile:` で表される、他家のアクションに対する反応フェーズ。
`kind` 属性（§3.4）ごとの検討対象:

| kind | 検討対象 |
|------|----------|
| `discard` | ロン / ポン / 大明槓 / チー（下家のみ）/ スルー |
| `riichi` | 同上。スルー確定でリーチ成立（供託+1、一発区間開始） |
| `kakan` | 槍槓ロンのみ |
| `ankan` | 国士無双の槍槓のみ（ルール依存） |

### 7.5 対象外の遷移状態

嶺上ツモ待ち（カン直後）、途中流局の判定中、和了宣言直後などの遷移状態は、
解析対象として撮影する意味が薄いため v0.x では対象外とする。

### 7.6 実装の参考（Swift）

```swift
enum Phase {
    case quiescent
    case awaitingDiscard(Player, DiscardContext)
    case awaitingClaim(Tile, from: Player, ClaimContext)
}

enum DiscardContext { case afterDraw, afterDrawRiichi, afterCall, unknown }
enum ClaimContext   { case discard, riichiDeclaration, kakan, ankan }
```

フェーズは解析コマンドの有効性チェック（例: `score X ron` は awaitingClaim でのみ有効）と、
REPL の状態遷移コマンド（`discard` / `pon` / `chi` など）の基盤となる。

## 8. イベントストリーム（[stream] セクション）

スナップショットを**初期局面（t0）**とし、そこからの時間発展をイベント列で記述できる。
チェスのPGN（FEN + 指し手列）に相当する構造。

```
[stream] format=paikei
{"type":"tsumo","actor":"self","pai":"6s"}
{"type":"dahai","actor":"self","pai":"1z","tsumogiri":false}
{"type":"pon","actor":"toimen","target":"self","pai":"1z","consumed":["1z","1z"]}
```

### 8.1 構文

- `[stream]` はファイル末尾に1つだけ置ける。以降の行は **JSON Lines**（1行1イベント）
- 空行と `#` 始まりの行は無視（JSON内の `#` は無関係）
- イベント語彙はMJAIプロトコルを踏襲する（`tsumo` `dahai` `chi` `pon` `daiminkan`
  `kakan` `ankan` `reach` `reach_accepted` `dora`（新ドラ表示）`hora` `ryukyoku`）

### 8.2 方言（format 属性）

| format | 牌表記 | actor表記 | 用途 |
|--------|--------|-----------|------|
| `paikei`（デフォルト） | MPSZ（赤=`0m`等） | `"self"` `"shimocha"` `"toimen"` `"kamicha"` | Paikeiネイティブ。カメラ/REPL出力 |
| `mjai` | MJAI（`E`〜`C`、`5mr`等） | 絶対座席 `0`〜`3` | 既存MJAIログの無変換貼り付け |

`format=mjai` の場合、絶対座席とカメラ相対の対応付けのため `self_actor` 属性が必須:

```
[stream] format=mjai self_actor=2
{"type":"tsumo","actor":2,"pai":"W"}
{"type":"dahai","actor":2,"pai":"W","tsumogiri":true}
```

MJAIの座順は反時計回りなので、`self_actor=n` から
shimocha = `(n+1)%4`、toimen = `(n+2)%4`、kamicha = `(n+3)%4` と導出する。

### 8.3 セマンティクス

- スナップショットが状態 t0。イベントを先頭から順に適用し、状態 t1, t2, ... を得る
- 解析は任意の時点 t に対して行える（REPL: `step` / `seek N` / 末尾が既定）
- **イベントは不明を減らすことはあっても増やすことはない**:
  - スナップショットで `?` だった値がイベントにより確定するのは正常
    （例: 他家の `dahai` でその牌が河に確定する）
  - イベントが既知の状態と**矛盾**する場合はエラー
    （例: `wall: 0` なのに `tsumo`、手牌に存在し得ない牌の `dahai`）
  - 他家のツモなど観測できない値は MJAI と同様 `"?"` を許容する
- `hora` / `ryukyoku` 以降のイベントは持たない（局をまたぐ場合は別ファイル）

### 8.4 ユースケース

- **動画解析**: キーフレームでスナップショットを1回起こし、以降は検出した打牌・鳴きを
  イベントとして追記（全フレームのフル認識より堅牢）。手出し/ツモ切り（`tsumogiri`）は
  連続フレームから検出できるため、ストリーム側では自然に埋まる
- **牌譜検討**: MJAI牌譜の `start_kyoku` をスナップショットへ変換し、以降を
  `format=mjai` でそのまま格納。任意の局面で止めて `analyze` できる
- **REPLセッション保存**: `discard` 等の遷移コマンドがイベントを生成するため、
  「初期局面 + 操作履歴」がそのまま保存・再現形式になる
- **遷移テスト**: 「この局面にこのイベント列を適用した結果」の回帰テストが書ける

## 9. サンプル

### 9.1 最小形（何切る・シャンテン計算用）

```
# minimal.paikei
hand: 123m456m789p55s11z
draw: 5s
```

### 9.2 対局中の全景

```
# east2-1.paikei — 東2局1本場、下家リーチ、対面ポンあり
bakaze: E
kyoku: 2
honba: 1
kyotaku: 1
```

## 10. 未解決の論点（v0.2以降で検討）

1. **一発の状態**: スナップショットに含めるか、解析コマンドの引数
   （`score 6s tsumo ippatsu`）に委ねるか。現状は後者の方針
   （槍槓は `claim_tile: ... kind=kakan` で表現可能になった）
2. **風が不明なときの点数計算**: §6は「`kyoku` / `seat` が不明なら『子・場風東と仮定』等の
   注記付きで答える」としているが、この仮定は**役を捏造しうる**。例えば `234m567p234s99p11z`
   に `1z` でロンした手は、東場と仮定すると場風1翻1300点になるが、実際が南場・西家なら
   役なしで和了できない。注記があっても答えが誤っている点は変わらない。
   実装（PaikeiCore）は次の方針を採る:
   - 不明な風は東南西北を**総当たりし、役と符が全候補で一致するかを確かめる**。
     一致するなら仮定は答えを変えないので黙って進む（国士無双や風牌のない手）。
     1つでも異なれば仮定せず、不足情報（`場風` / `席風`）を宣言して断る
   - 席風の**親子の別だけは**「子（南家）」と仮定し、支払いが変わる旨を注記する。
     役・符が風によらないと確認済みのケースに限られるため、誤るのは支払いのみ
   - 仮定として提示するのは「外れていれば答えがより高くなる」ものだけに限る
     （本場・供託・ドラ・立直の不明）。役満ではドラを数えないため、その場合は
     ドラ不明も注記しない
   **§6を上記の方針に改訂済み**（旧「子・場風東と仮定」「自風により変動と幅で答える」）。
   残る論点は、断る代わりに幅で答える形式（「東場なら1300点 / それ以外は役なし」）を
   別途定義するか。定義するなら候補を列挙する結果型が要る。
3. **ルールプリセット**（`rule:`）の中身: 喰いタン、赤の枚数、切り上げ満貫など
4. **ストリーム途中のチェックポイントスナップショット**: 長いストリームの再同期・
   認識誤り訂正用に、スナップショットを複数持てる形式にするか
   （単純な時系列格納は §8 で解決済み）
5. **北抜き（三麻）対応**: v0.xでは四麻のみを対象とする
6. **§7.5の遷移状態**（嶺上ツモ待ちなど）を将来サポートするか
7. **状態属性 `*`/`^` の併記順**（§5）: §5冒頭は「打牌属性 → 状態属性」とするが、
   状態属性どうし（`*` と `^`）の順序を明示していない。属性表の並びは `*`→`^` だが、
   本文の散文では宣言牌が鳴かれた例を `^*` と表記しており食い違う。
   実装（PaikeiCore）は**正規形を `*`→`^`（例: `4m+*^`）**とし、パースは順不同を受理する。
   仕様として `*`→`^` を正典化するか要確認。
